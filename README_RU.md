# Модуль воспроизведения LLM-трасс в ns-3

[English version](README.md)

Этот внешний модуль ns-3 воспроизводит сетевой обмен, записанный в трассах
нагрузки больших языковых моделей (LLM), поверх инфраструктурной сети
802.11ax. Он распределяет агентов прикладного уровня между точками доступа
(AP) и станциями (STA), устанавливает TCP-соединения, планирует восходящие и
нисходящие передачи заданного трассой размера и сообщает, что наблюдали
прикладной уровень, MAC и PHY.

Самая важная мысль:

> Проект не запускает LLM и не моделирует генерацию токенов. Он воспроизводит
> временные отметки и размеры сетевых передач, полученные из LLM-нагрузки.

Стандартный пример создает три изолированных базовых набора обслуживания
(BSS). В каждом BSS находится одна AP и 30 физических STA. На одной физической
STA может работать много прикладных агентов. Модуль также содержит независимый
калибровочный Wi-Fi-бенчмарк насыщенного TCP, который не воспроизводит трассы.

## Цели и не-цели

### Основные цели

1. Воспроизводить сетевой обмен LLM-агентов с исходным временем из трассы.
2. Исследовать влияние распределения агентов на конкуренцию в Wi-Fi.
3. Измерять прохождение прикладной полезной нагрузки через TCP, Wi-Fi MAC и
   Wi-Fi PHY.
4. По возможности отделять первые передачи от повторных.
5. Формировать разреженную машиночитаемую статистику по BSS и STA.
6. Обрабатывать большие трассы с ограниченным потреблением памяти.
7. Обеспечивать воспроизводимость за счет детерминированных правил размещения
   и фиксированных значений seed/run генератора случайных чисел ns-3.

### Что проект не делает

- Не моделирует инференс LLM, выбор токенов, работу GPU, расход памяти или
  качество модели.
- Не предсказывает реальную длительность инференса. `durationMs` берется из
  входной трассы и не вычисляется заново по `model`, `inputToken` или
  `outputToken`.
- Не сертифицирует соответствие IEEE 802.11 или совместимость Wi-Fi Alliance.
- Не воспроизводит частотный план конкретного регуляторного домена.
- Не моделирует интерференцию между тремя стандартными BSS. Они намеренно
  используют разные объекты канала.
- Не включает автоматически все функции 802.11ax. В частности, сценарий не
  подключает многопользовательский планировщик, поэтому OFDMA явно не включен.

## Как работает модель

```text
JSON-трасса
  -> разбор операций агентов и длительности эксперимента
  -> оценка пересечения восходящих передач по временным слотам
  -> распределение агентов между BSS
  -> распределение агентов между физическими STA
  -> создание AP, STA, Wi-Fi-устройств, IP-адресов и TCP-приложений
  -> ожидание TCP-соединения у каждого генератора трафика
  -> выбор общей эпохи эксперимента
  -> воспроизведение UL/DL-передач относительно этой эпохи
  -> перенос прикладных метаданных через TCP с помощью AppTxTag
  -> наблюдение попыток MAC/PHY, эфирного времени, скорости, задержек,
     повторов и потерь
  -> запись единого JSON по окнам с общей статистикой AP/STA
```

Для достижения цели используются пять основных методов:

1. **Сокращение трассы:** в C++-модель попадают только поля, необходимые для
   воспроизведения времени и размеров передач.
2. **Размещение с учетом конкуренции:** агенты с пересекающимся UL-трафиком
   распределяются между BSS, а затем группируются за физическими STA.
3. **Глобальный барьер готовности:** нулевая отметка трассы общая для всех
   генераторов и не зависит от порядка установки TCP-соединений.
4. **Маркировка байтов:** `AppTxTag` следует за диапазоном прикладных байтов,
   когда TCP разделяет или объединяет записи.
5. **Межуровневый учет:** прикладные callback-функции, трассы MAC, трассы PHY и
   состояния PHY накапливаются отдельно и сравниваются.

## Стандартный сценарий

Исполняемая программа называется `llm-scenario`. Типизированные значения по
умолчанию заданы в [`ScenarioConfig`](examples/config/scenario-config.h), а
полная документированная конфигурация запуска находится в
[`config/llm_config.toml`](config/llm_config.toml).

| Параметр | Значение | Смысл |
|---|---:|---|
| Число BSS | 3 | Три независимые группы AP |
| Физических STA в BSS | 30 | Всего 90 физических STA |
| Стандарт Wi-Fi | 802.11ax | ns-3 `WIFI_STANDARD_80211ax` |
| Диапазон | 5 ГГц | `BAND_5GHZ` |
| Ширина канала | 20 МГц | TOML/CLI также принимает 40, 80 и 160 МГц |
| Номер канала | 0 | ns-3 выбирает первый допустимый канал для стандарта/диапазона/ширины |
| Индекс основного 20-МГц канала | 0 | Самый низкочастотный основной подканал 20 МГц |
| Алгоритм скорости | MinstrelHt | Динамический выбор скорости; текущий ns-3 содержит HE-группы |
| Положение AP для BSS `i` | `(100i, 100i, 100i)` м | Постоянная позиция |
| Размещение STA | Равномерно в диске 5 м | Центр диска совпадает с AP |
| TCP-порт приемника AP | 10000 | Принимает восходящий трафик STA |
| TCP-порты приемников STA | 9000 + индекс STA | Принимают нисходящий трафик AP |
| Начало настройки генераторов | 1 с | Начинается TCP-подключение, а не полезный трафик |
| RNG seed/run | 12345 / 1 | Воспроизводимое случайное размещение |
| Окно статистики | 10 мс | Единые разреженные интервальные измерения |
| Запас в автоматическом режиме | 2 с | Добавляется к длительности трассы |

По умолчанию каждый BSS использует собственный `YansWifiChannel`.
`YansWifiChannelHelper::Default()` применяет
`ConstantSpeedPropagationDelayModel` и `LogDistancePropagationLossModel`.
При изолированных каналах передача в BSS 0 не может мешать устройству в BSS 1
или 2, даже если их номинальные настройки канала или координаты пересекаются.
При `topology.isolate_bss_channels = false` все BSS получают один объект
канала, поэтому передачи разделяют моделируемую среду.

Ассоциация в инфраструктурной сети выполняется настоящей MAC-логикой ns-3:
каждый BSS имеет уникальный SSID (`llm-ap-0`, `llm-ap-1` или `llm-ap-2`), AP
используют `ApWifiMac`, STA используют `StaWifiMac`, а STA выполняют активное
сканирование. События ассоциации записываются через трассу `Assoc`.

### Адресация

Для BSS `i`:

```text
AP:      10.1.i.1:10000
STA 0:   10.1.i.2:9000
STA 1:   10.1.i.3:9001
...
STA 29:  10.1.i.31:9029
```

Один генератор AP обслуживает всех нисходящих агентов своего BSS и держит по
одному TCP-сокету на каждую используемую физическую STA. Один генератор STA
обслуживает всех восходящих агентов, назначенных этой STA, и использует для
них общий TCP-сокет.

## Формат трассы и использование полей

C++-парсер загружает JSON-объект с массивом `traces` верхнего уровня. Большие
RAR-файлы сначала нужно сократить потоковыми инструментами, описанными ниже:
сам C++-парсер строит DOM всего JSON.

### Поля, используемые C++-симулятором

| Путь JSON | Обязательно | Использование |
|---|---|---|
| `traces[].agentId` | Да | Числовая часть ключа агента |
| `traces[].agentType` | Да | Строковая часть ключа и детерминированный ID типа |
| `traces[].tasks` | Да | Контейнер, который обходит парсер |
| `tasks[].operations` | Да | Контейнер, который обходит парсер |
| `operations[].startOffsetMs` | Да | Время отправки UL относительно эпохи трассы, мс |
| `operations[].durationMs` | Да | Добавляется к началу для получения времени DL |
| `operations[].uplinkBytes` | Да | Полезная нагрузка, отправляемая STA |
| `operations[].downlinkBytes` | Да | Полезная нагрузка, отправляемая AP |

Ключ агента имеет вид:

```text
<agentId>_<agentType>
```

Например, ID `7` и тип `planner` дают ключ `7_planner`.

Операция воспроизводится как сетевой трафик только тогда, когда **оба** поля
байтов положительны. Если `uplinkBytes <= 0` или `downlinkBytes <= 0`,
C++-генераторы не планируют эту операцию. Однако ее
`startOffsetMs + durationMs` по-прежнему влияет на вычисленную длительность
эксперимента.

### Пример времени операции

Вход:

```json
{
  "startOffsetMs": 100.0,
  "durationMs": 25.0,
  "uplinkBytes": 80,
  "downlinkBytes": 200
}
```

Воспроизведение:

```text
время трассы 100 мс: STA отправляет 80 байт UL своей AP
время трассы 125 мс: AP отправляет 200 байт DL этой STA
```

Таким образом, `durationMs` задает интервал между загрузкой запроса и
выгрузкой ответа. Это время из трассы, а не вычисленное время инференса.

### Поля, сохраняемые, но игнорируемые C++-симулятором

Реальные трассы также содержат:

- корневой `metadata` (`source`, `generator`, количество устройств);
- поля трассы `hostId` и `edgeDevice`;
- поля задачи `taskSequence`, `taskType`, `arrivalOffsetMs`, ссылки на
  исходного агента и `callRef`;
- поля операции `opId`, `operationType`, `operatorCategory`, `name`, счетчики
  токенов, `model`, `serverHostId` и `depend`.

Потоковые скрипты сохраняют эти поля при создании среза. Они переводят
`startOffsetMs` и числовой `arrivalOffsetMs` в систему времени нового окна и
удаляют из `depend` ссылки на исключенные операции. C++-симулятор сейчас
игнорирует дополнительные поля. В частности, число токенов и имя модели не
влияют на размер пакета, длительность, размещение, PHY-скорость или метрики.

### Числовые ограничения

[`stream.py`](scripts/trace_tools/stream.py) проверяет те же важные границы,
что и C++-парсер:

- `agentId` должен помещаться в знаковое 32-битное целое;
- поля байтов должны быть целыми в `[0, INT_MAX]`;
- смещения и длительности должны быть конечными и неотрицательными;
- сумма `startOffsetMs + durationMs` должна оставаться конечной.

## Распределение агентов

Пример вызывает `DistributeAgentsContentionAware()` в две фазы.

### Фаза 1: распределение по BSS

Каждая сетевая операция отмечает фиксированный слот, содержащий начало ее
восходящей передачи. Стандартная ширина слота равна 10 мс. Агенты, занятые в
одинаковых UL-слотах, считаются пересекающимися.

Алгоритм многократно выбирает еще не назначенного агента с наибольшим числом
оставшихся пересечений и помещает его в BSS с наименьшим приростом парных
UL-конфликтов. При равенстве выбирается:

1. BSS с меньшим уже назначенным числом байтов;
2. BSS с меньшим числом агентов;
3. BSS с меньшим индексом.

Фаза старается разнести пересекающихся агентов по независимым BSS.

### Фаза 2: распределение по STA

В стандартном примере `lowContentionPriority = true`. Предпочтение отдается
STA, которая уже активна в тех же UL-слотах. Тогда несколько прикладных
агентов используют одного физического претендента на среду вместо нескольких
конкурирующих STA.

Простой пример:

```text
Агент A использует слоты {10, 11}
STA 0 уже использует слоты {10, 11}
STA 1 уже использует слоты {20, 21}

Размещение A на STA 0 добавляет 0 активных пар STA/слот.
Размещение A на STA 1 добавляет 2 активные пары STA/слот.
Режим низкой конкуренции выбирает STA 0.
```

Если `lowContentionPriority = false`, алгоритм сначала задействует максимально
возможное число физических STA агентами с малой взаимной близостью, а затем
применяет размещение с учетом близости.

Стандартный пример ограничивает число прикладных агентов на физическую STA
значением 832. При 3 BSS и 30 STA на BSS общая емкость равна:

```text
3 * 30 * 832 = 74 880 прикладных агентов
```

Это не ограничение числа станций в IEEE 802.11. Это ограничение прикладной
модели, используемое алгоритмом размещения.

## Время трафика и барьер готовности

Запуск приложения в момент 1 с начинает только настройку TCP. Полезные
передачи не планируются, пока каждый генератор AP и используемой STA не
сообщит о готовом TCP-соединении.

Когда готов последний генератор, `TrafficCoordinator` выбирает первую целую
секундную границу строго после текущего времени:

```text
все сокеты готовы в 1,37 с -> общая эпоха трассы равна 2,00 с
```

Все генераторы планируют нулевое смещение трассы относительно одной эпохи.
Поэтому раннее TCP-соединение не начинает нагрузку раньше более медленного.

Приложения останавливаются в момент:

```text
общая эпоха + настроенная длительность эксперимента
```

Режимы длительности внутри используют миллисекунды:

```text
auto:  maximum_duration_ms = trace_duration_ms + auto_tail_seconds * 1000
fixed: maximum_duration_ms = fixed_duration_seconds * 1000
```

Если фиксированная длительность короче трассы, выводится предупреждение об
обрезании хвоста.

### Особенность настройки TCP

Настроенный TypeId алгоритма управления перегрузкой проверяется как подкласс
`TcpCongestionOps` и задается в `TcpL4Protocol::SocketType` до создания любого
Internet stack. Размер сегмента и буферов отправки/приема также задается до
того, как приложения создают сокеты. Поэтому конфигурация по умолчанию
использует `TcpHighSpeed`, сегменты 1460 байт и буферы 32 МиБ без поздней
замены алгоритма.

## Связь прикладного уровня с PHY

TCP может разделить одну прикладную запись на несколько сегментов или
объединить записи. Поэтому одного идентификатора пакета недостаточно для
межуровневого учета.

Перед отправкой через сокет генератор добавляет байтовый тег `AppTxTag`:

- UID прикладного пакета;
- время прикладной отправки в микросекундах;
- IPv4-адреса источника и назначения;
- TCP-порты источника и назначения;
- число байтов прикладной нагрузки;
- ключ агента.

Будучи байтовым тегом, метаданные следуют за диапазоном полезной нагрузки при
сегментации и агрегации TCP.

При передаче на PHY:

1. в полезной нагрузке MPDU находятся диапазоны с тегом;
2. по адресам определяются BSS, STA и направление;
3. тегированные байты добавляются в настроенное окно статистики;
4. первая наблюдаемая передача добавляет уникальные байты и задержку
   от приложения до PHY;
5. повторный идентификатор MPDU увеличивает счетчик повторных передач;
6. длительность PPDU и номинальная скорость TXVECTOR распределяются между
   представленными потоками.

Если PPDU содержит несколько тегированных потоков, эфирное время делится
пропорционально числу тегированных байтов. Пример:

```text
длительность PPDU: 100 мкс
тегированные байты потока A: 300
тегированные байты потока B: 100

выделенное эфирное время A: 75 мкс
выделенное эфирное время B: 25 мкс
```

Номинальная PHY-скорость не равна прикладной полезной пропускной способности.
Это скорость, выбранная в `WifiTxVector` для фактической попытки PPDU.

## Выходные метрики

Эксперимент записывает один JSON-документ, организованный сначала по окнам.
`general.output_name` задает имя файла внутри папки запуска; по умолчанию это
`output.json`. Файл создается эксклюзивно: существующий путь никогда не
обрезается и не перезаписывается. `output.json` всегда записывается потоково с
отступом в два пробела и завершающим переводом строки, без построения полного
DOM результата в памяти. Возможности компактного вывода нет. Читаемый формат
не меняет схему и значения, но занимает на диске больше места, чем
эквивалентный компактный JSON.

По явному решению о совместимости целое поле `schema_version` остается равным
`1`, но эта иерархия является несовместимой заменой на месте. Для удаленных
корней `wifi_windows`, `wifi_summary`, `transmission_summary` и
`cross_layer_summary` нет псевдонимов; записей с фиксированными секундными
интервалами тоже нет. Потребителей прежнего документа версии 1 нужно перевести
на приведенную ниже иерархию.

Все итоговые измерения эксперимента находятся только в JSON. Удаленные
финальные заголовки и строки отчетов генераторов AP и STA, приемников, передачи
и межуровневой статистики не печатаются в stdout или логи ns-3. Обычные
сообщения о запуске, событиях, ходе, ошибках и завершении сохраняются.

### Модель по окнам и корневая схема

`statistics.window_ms` задает единую интервальную шкалу для измерений
приложения, TCP, устройства, MAC, PHY и межуровневых данных. Вывод разрежен по
окнам и сущностям: полностью неактивное окно отсутствует, а неактивная сущность
не входит в выведенное окно. Однако появившаяся сущность всегда содержит все
фиксированные категории и оба направления. `overall` устроен иначе: он плотный
и содержит каждую зарегистрированную AP и STA, включая полностью нулевые.

Запись AP является родительским агрегатом своего BSS, а записи STA дают
дочернюю детализацию по устройствам. Дублирование родителя и дочерних записей
намеренно. Например:

```text
STA 0 uplink accepted payload: 1000 bytes
STA 1 uplink accepted payload: 2000 bytes
AP 0 uplink accepted payload:  3000 bytes
```

Семь корневых полей физически записываются в показанном порядке:

```json
{
  "schema_version": 1,
  "measurement_semantics": {},
  "statistics_window_ms": 10,
  "windows": [],
  "overall": {
    "access_points": [],
    "stations": []
  },
  "validation": {},
  "experiment_metadata": {
    "configuration": {},
    "entity_inventory": {
      "access_points": [],
      "stations": []
    }
  }
}
```

| Корневое поле | Единица | Смысл |
|---|---:|---|
| `schema_version` | целое | Версия схемы, строго `1` |
| `measurement_semantics` | объект | Машиночитаемое описание родителя/дочерних данных, нагрузки, средних, разреженности и `null` |
| `statistics_window_ms` | мс | Настроенная ширина интервала |
| `windows` | массив | Разреженные записи настроенных окон |
| `overall` | объект | Плотные записи AP/STA за весь эксперимент |
| `validation` | объект | Восемь флагов согласованности сырых итогов |
| `experiment_metadata` | объект | Эффективная конфигурация и плотный реестр сущностей; записывается последним |

`measurement_semantics` содержит следующие точные поля:

| Поле | Смысл |
|---|---|
| `access_point_role` | Объекты AP являются записями `BSS parent aggregate` |
| `station_role` | Объекты STA являются записями `per-station child detail` |
| `parent_child_duplication` | Дублирование родителя и дочерних данных имеет значение `intentional` |
| `mac_tcp_payload_bytes` | Значения TCP-нагрузки MAC являются `header-based estimates` |
| `phy_tagged_payload_bytes` | Включены попытки и повторные передачи |
| `phy_unique_tagged_payload_bytes` | Включены только первые передачи тегированных MPDU |
| `phy_average_data_rate` | Номинальная скорость взвешена по эфирному времени |
| `congestion_window` | CWND взвешено по времени для каждого соединения |
| `sample_distributions` | Задержки, RTT, интервалы между приемами и длительности взвешены по выборкам |
| `sparse_window_absence` | Отсутствие означает нулевую активность |
| `undefined_derived_values` | Всегда JSON `null` |

### Границы окон, владение событиями и идентичности

Границы окон отсчитываются от общей эпохи эксперимента:

```text
window_us = statistics_window_ms * 1000
window_index = floor(relative_time_us / window_us)
window_start_ms = window_index * statistics_window_ms
window_duration_ms = min(statistics_window_ms,
                         experiment_duration_ms - window_start_ms)
```

`window_duration_ms` содержит фактическую положительную длительность. Обычно
она равна настроенной ширине; последнее частичное окно может быть короче или
дробным. При ширине 25 мс и длительности эксперимента 35 мс возможны два окна
длительностью 25 мс и 10 мс. Каждая скорость и загрузка использует фактическую
длительность.

Точечное наблюдение принадлежит окну, содержащему его временную метку. Это
относится к принятым отправкам, прикладным отбросам и приемам, выборкам RTT,
отбросам/ошибкам MAC и попыткам PHY. Сопоставленное измерение TX/RX устройства
принадлежит окну события передачи, даже если прием произошел позже. Интервал
между приемами записывается в окно более позднего приема и независимо
отслеживается для сущности, направления и узла-партнера. Задержка от приложения
до PHY для первой передачи относится к направлению отправителя и окну этой
попытки PHY.

Наблюдения длительности или состояния не помещаются целиком в начальное окно.
Интервалы занятости PHY и ступенчатое состояние CWND пересекаются с каждым
настроенным окном, которое они охватывают; в окно попадают только микросекунды
пересечения. Изменения CWND до эпохи задают начальное значение без добавления
времени до эпохи, а финальное состояние интегрируется до конца эксперимента.

Каждое окно имеет следующую точную форму:

```json
{
  "window_index": 42,
  "window_start_ms": 420,
  "window_duration_ms": 10,
  "access_points": [],
  "stations": []
}
```

| Поле окна | Единица | Смысл |
|---|---:|---|
| `window_index` | индекс | Нулевой индекс настроенного окна |
| `window_start_ms` | мс | Начало относительно эпохи эксперимента |
| `window_duration_ms` | мс | Фактическая полная или частичная длительность |
| `access_points` | массив | Активные родительские агрегаты AP/BSS в порядке `access_point_id` |
| `stations` | массив | Активные дочерние записи STA в порядке `(access_point_id, station_index)` |

Поля идентичности AP: `access_point_id` (нулевой ID BSS), `node_id` (ID узла
ns-3), `node_label` (стабильная метка) и `ipv4` (строка адреса). Идентичность
STA дополнительно содержит нулевой внутри BSS `station_index` и сохраняет
`access_point_id` родителя. Узлы-партнеры упорядочены по ID узла/IP, агенты по
`agent_key`, причины MAC по числовому `reason_code`.

Правила объединения родителя BSS:

- статистика отправителя AP downlink возникает на AP и детализируется по STA
  назначения;
- статистика отправителя AP uplink объединяет отправителей uplink связанных
  STA;
- статистика приемника AP uplink возникает в приемнике/устройстве AP;
- статистика приемника AP downlink объединяет данные приемников/устройств
  связанных STA;
- массивы TCP в AP сохраняют независимые соединения AP-to-STA и STA-to-AP;
- направленные итоги нагрузки MAC/PHY для AP объединяют дочерние потоки BSS, а
  записи STA сохраняют приписанную им детализацию;
- занятость и загрузка PHY для AP используют только PHY точки доступа как
  эталон BSS; время занятости STA к нему не суммируется.

### Фиксированная форма сущности и правила производных значений

Каждая выведенная и общая сущность содержит описанные поля идентичности и
следующую фиксированную форму:

```json
{
  "general_stats": {"uplink": {}, "downlink": {}},
  "app_stats": {"uplink": {}, "downlink": {}},
  "tcp_stats": {"uplink": {}, "downlink": {}},
  "mac_stats": {"uplink": {}, "downlink": {}},
  "phy_stats": {
    "busy_time_us": 0,
    "channel_utilization_percent": 0.0,
    "uplink": {},
    "downlink": {}
  }
}
```

`uplink` означает STA -> AP, а `downlink` означает AP -> STA. Занятость и
загрузка PHY являются локальным ненаправленным состоянием, поэтому остаются на
уровне категории.

Счетчики, байты, длительности и известные скорости при отсутствии активности
равны числовому нулю; массивы детализации пусты. Производное среднее, доля,
скорость, минимум, максимум или отклонение равно `null`, если знаменатель или
набор выборок не определен. При известной положительной длительности и нулевой
нагрузке пропускная способность равна числовому `0.0`, а не `null`. Значения
выводятся из сырых аккумуляторов; рассчитанные средние отдельных окон никогда
не усредняются повторно.

Общие формулы:

```text
window_throughput_mbps = payload_bytes * 8 / actual_window_duration_us
overall_throughput_mbps = total_payload_bytes * 8 / experiment_duration_us

sample_average_us = sum(sample_us) / sample_count
sample_population_standard_deviation_us =
  sqrt(sum((sample_us - sample_average_us)^2) / sample_count)

bandwidth_share_percent = child_payload_bytes / direction_payload_bytes * 100

average_phy_rate_mbps =
  sum(data_rate_bps * allocated_airtime_us) / total_airtime_us / 1e6

channel_utilization_percent =
  min(100, busy_time_us / denominator_duration_us * 100)

average_congestion_window_bytes =
  sum(cwnd_bytes * observation_duration_us) / total_observation_duration_us
```

Байты, умноженные на восемь и разделенные на микросекунды, непосредственно
дают Mbps. Доли отдельно вычисляются для принятых и полученных направленных
итогов; общие доли используют байты всего эксперимента.

### `general_stats`

Каждое направление содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `estimated_transmitted_tcp_payload_bytes` | байты | Разобранная TCP-нагрузка в событиях `MacTx` устройства при постановке пакета в очередь |
| `estimated_matched_tcp_payload_bytes` | байты | Нагрузка в сопоставлениях TX/RX с положительной длительностью |
| `matched_packet_count` | количество | Сопоставленные пакеты с положительной длительностью |
| `total_transmission_duration_us` | мкс | Сумма длительностей прием минус передача |
| `average_transmission_duration_us` | мкс или `null` | Среднее арифметическое сопоставленных длительностей |
| `transmission_duration_standard_deviation_us` | мкс или `null` | Популяционное отклонение сопоставленных длительностей |
| `minimum_transmission_duration_us` | мкс или `null` | Минимальная положительная сопоставленная длительность |
| `maximum_transmission_duration_us` | мкс или `null` | Максимальная положительная сопоставленная длительность |
| `effective_throughput_mbps` | Mbps или `null` | Скорость сопоставленной нагрузки за сопоставленную длительность |
| `application_to_phy_delay` | объект | Распределение задержки от приложения до PHY для первой передачи |

Нагрузка оценивается после разбора заголовков LLC/SNAP, IPv4 и TCP.
Событие `MacTx` устройства возникает при постановке пакета в очередь MAC Wi-Fi.
Поэтому пакет, повторно переданный TCP, может появиться как новая постановка в очередь,
но повторная попытка 802.11 уже поставленного MPDU не является новым событием
`MacTx` устройства; попытки и повторы Wi-Fi измеряются в `phy_stats`.
Сопоставление использует адреса, порты, оценочный размер нагрузки и порядок
наблюдения. Это диагностика, а не метрика ns-3 `FlowMonitor`. Формула категории:

```text
effective_throughput_mbps =
  estimated_matched_tcp_payload_bytes * 8 / total_transmission_duration_us
```

Без положительного сопоставления количество, байты и общая длительность равны
нулю, а все четыре производных поля длительности и
`effective_throughput_mbps` равны `null`.

Каждое распределение выборок (`application_to_phy_delay`,
`receive_interarrival_time` и `round_trip_time`) имеет поля:

| Поле | Единица | Смысл |
|---|---:|---|
| `sample_count` | количество | Число сырых выборок |
| `average_us` | мкс или `null` | Среднее арифметическое выборок |
| `standard_deviation_us` | мкс или `null` | Популяционное стандартное отклонение |
| `minimum_us` | мкс или `null` | Минимальная выборка |
| `maximum_us` | мкс или `null` | Максимальная выборка |

Все четыре производных поля равны `null`, когда `sample_count` равен нулю.

### `app_stats`

Каждое направление содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `accepted_send_count` | количество | Вызовы `Socket::Send`, принявшие положительную нагрузку |
| `accepted_payload_bytes` | байты | Фактически принятые TCP байты, не запрошенное число |
| `accepted_throughput_mbps` | Mbps или `null` | Принятые байты за длительность окна/эксперимента |
| `receive_event_count` | количество | Вызовы приемника |
| `received_payload_bytes` | байты | Байты, доставленные приемнику |
| `received_throughput_mbps` | Mbps или `null` | Полученные байты за длительность окна/эксперимента |
| `drop_event_count` | количество | Неудачные или частично отклоненные прикладные отправки |
| `dropped_payload_bytes` | байты | Нагрузка, не принятая TCP |
| `receive_interarrival_time` | объект | Распределение интервалов приема для каждого партнера |
| `agents` | массив | Детализация отправителей/отбросов в порядке `agent_key` |
| `peers` | массив | Детализация отправителей/приемников/отбросов по партнерам |

Запись `agents` содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `agent_key` | строка | Стабильный ключ агента трассы |
| `accepted_send_count` | количество | Принятые отправки агента |
| `accepted_payload_bytes` | байты | Принятые байты агента |
| `accepted_throughput_mbps` | Mbps или `null` | Скорость принятой нагрузки агента |
| `accepted_bandwidth_share_percent` | проценты или `null` | Байты агента, деленные на принятые байты направления |
| `drop_event_count` | количество | Прикладные отбросы агента |
| `dropped_payload_bytes` | байты | Отброшенная нагрузка агента |

Запись `peers` содержит `peer_node_id` и `peer_ipv4`, затем
`accepted_send_count`, `accepted_payload_bytes`, `accepted_throughput_mbps`,
`accepted_bandwidth_share_percent`, `receive_event_count`,
`received_payload_bytes`, `received_throughput_mbps`,
`received_bandwidth_share_percent`, `drop_event_count` и
`dropped_payload_bytes` с теми же единицами и смыслом, что у полей направления
или агента. Принятые и полученные значения намеренно не обязаны совпадать из-за
буферизации, отсечения и поведения TCP.

### `tcp_stats`

Каждое направление имеет массив `connections`. Соединение с партнером содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `peer_node_id` | ID узла | Ссылка на партнера в реестре |
| `peer_ipv4` | адрес IPv4 | Адрес партнера из реестра |
| `congestion_window_observation_duration_us` | мкс | Общая длительность наблюдаемого состояния CWND |
| `average_congestion_window_bytes` | байты или `null` | Взвешенное по времени CWND |
| `last_congestion_window_bytes` | байты или `null` | Последнее наблюдаемое CWND |
| `round_trip_time` | объект | Распределение выборок RTT |

CWND независимых сокетов партнеров никогда не объединяется. Среднее равно
`null` без положительной длительности наблюдения, последнее значение равно
`null`, если его не наблюдали, а производные RTT равны `null` без выборок.

### `mac_stats`

Каждое направление содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `estimated_transmit_event_count` | количество | События `MacTx` устройства при постановке пакетов с нагрузкой в очередь |
| `estimated_transmitted_tcp_payload_bytes` | байты | Оценочная TCP-нагрузка в этих постановках в очередь |
| `estimated_transmit_throughput_mbps` | Mbps или `null` | Оценочная скорость TX-нагрузки |
| `estimated_receive_event_count` | количество | События разобранной нагрузки RX MAC |
| `estimated_received_tcp_payload_bytes` | байты | Оценочная полученная TCP-нагрузка |
| `estimated_receive_throughput_mbps` | Mbps или `null` | Оценочная скорость RX-нагрузки |
| `transmit_drop_count` | количество | Вызовы отброса передачи MAC |
| `transmit_drop_packet_bytes` | байты | Полные байты пакетов из вызовов отброса передачи |
| `mpdu_drop_count` | количество | Отброшенные MPDU |
| `mpdu_drop_bytes` | байты | Полные байты отброшенных MPDU |
| `data_failure_count` | количество | Вызовы ошибки данных MAC |
| `final_data_failure_count` | количество | Финальные вызовы ошибки данных MAC |
| `mpdu_drops_by_reason` | массив | Итоги `{reason_code, drop_count}` в числовом порядке причин |
| `peers` | массив | Разрешенная детализация MAC по партнерам |

Запись партнера MAC начинается с `peer_node_id` и `peer_ipv4`, затем содержит
`estimated_transmit_event_count`, `estimated_transmitted_tcp_payload_bytes`,
`estimated_transmit_throughput_mbps`, `estimated_receive_event_count`,
`estimated_received_tcp_payload_bytes`, `estimated_receive_throughput_mbps`,
`mpdu_drop_count`, `mpdu_drop_bytes`, `data_failure_count`,
`final_data_failure_count` и `mpdu_drops_by_reason`. Единицы совпадают с
таблицей направления. Наблюдения, для которых партнер не разрешен, остаются
только в итогах направления.

### `phy_stats`

Поля уровня категории:

| Поле | Единица | Смысл |
|---|---:|---|
| `busy_time_us` | мкс | Пересечение локальных PHY TX, RX и CCA_BUSY с длительностью знаменателя |
| `channel_utilization_percent` | проценты или `null` | Доля занятого времени, не более 100 процентов |

Каждое направление содержит:

| Поле | Единица | Смысл |
|---|---:|---|
| `tagged_payload_bytes` | байты | Тегированные байты всех попыток с повторами |
| `unique_tagged_payload_bytes` | байты | Тегированные байты только первой наблюдаемой передачи MPDU |
| `tagged_mpdu_count` | количество | Попытки полных тегированных MPDU |
| `complete_tagged_mpdu_bytes` | байты | Полные байты попыток тегированных MPDU |
| `transmission_attempt_count` | количество | Попытки тегированных передач |
| `retransmission_count` | количество | Повторные идентичности тегированных MPDU |
| `transmission_airtime_us` | мкс | Эфирное время PPDU, распределенное пропорционально тегированным байтам |
| `average_data_rate_mbps` | Mbps или `null` | Взвешенная по эфирному времени номинальная скорость `WifiTxVector` |
| `throughput_mbps` | Mbps или `null` | Скорость тегированной нагрузки за длительность знаменателя |
| `peers` | массив | Разрешенная детализация PHY по партнерам |

Запись партнера PHY содержит `peer_node_id`, `peer_ipv4`,
`tagged_payload_bytes`, `unique_tagged_payload_bytes`,
`transmission_attempt_count`, `retransmission_count`,
`transmission_airtime_us`, `average_data_rate_mbps` и `throughput_mbps` с теми
же единицами и смыслом. Число/байты полных MPDU остаются на уровне направления,
поскольку один MPDU может нести несколько тегированных диапазонов партнеров.
Эфирное время управляющих и служебных кадров влияет на локальное
`busy_time_us`, но не имеет тегированной нагрузки партнера.

`average_data_rate_mbps` равно `null` без распределенного эфирного времени.
`channel_utilization_percent` и `throughput_mbps` равны `null` только без
допустимого знаменателя; при допустимой длительности нулевая занятость или
нагрузка дает числовой ноль.

### Плотный overall, проверка и метаданные

`overall.access_points` и `overall.stations` используют в точности ту же форму
идентичности, категорий, направлений и вложенных полей. Они содержат каждую
сущность реестра. Перед расчетом результатов объединяются сырые аккумуляторы
окон: пропускная способность использует общую длительность эксперимента,
распределения объединяют сырые выборки, скорость PHY -- произведения
скорость-время, CWND -- произведения байты-время, а доли -- направленные байты
всего эксперимента.

Для допустимого запуска все восемь полей `validation` должны быть равны `true`:

| Поле | Проверка |
|---|---|
| `entity_inventory_references_valid` | Каждая сущность и разрешенный партнер ссылаются на идентичность/адрес из реестра |
| `app_agent_totals_consistent` | Итоги принятых данных/отбросов агентов укладываются в итоги направления приложения |
| `app_peer_totals_consistent` | Итоги разрешенных партнеров укладываются в итоги направления приложения |
| `mac_peer_totals_consistent` | Итоги партнеров и причин MAC согласованы с итогами направления |
| `phy_peer_totals_consistent` | При полностью разрешенной атрибуции сырые итоги партнеров PHY совпадают с итогами направления |
| `ap_station_sender_totals_consistent` | Восстановленные родительские итоги отправителя AP/BSS совпадают с сырыми локальными данными AP и дочерними данными STA |
| `overall_matches_windows` | Плотные сырые общие значения равны объединению всех настроенных окон, включая пропущенные пустые |
| `unique_phy_payload_within_tagged_payload` | Уникальная PHY-нагрузка не превышает тегированную нагрузку всех попыток |

Проверка сравнивает целые/сырые значения аккумуляторов до округления JSON. Она
не сравнивает принятые байты отправителя с полученными байтами приемника.

`experiment_metadata.entity_inventory` является плотным, не содержит
статистики и детерминированно упорядочен. Записи AP содержат
`access_point_id`, `node_id`, `node_label` и `ipv4`; записи STA дополнительно
содержат `station_index`.

`experiment_metadata.configuration` записывает финальные значения реестра
после:

```text
compiled defaults < TOML values < CLI overrides
```

Точные восемь секций и 36 выходных полей:

| Объект | Эффективные поля |
|---|---|
| `general` | `trace_file`, `run_folder`, `output_name` |
| `simulation` | `duration_mode`, `fixed_duration_seconds`, `auto_tail_seconds`, `rng_seed`, `rng_run` |
| `topology` | `bss_count`, `stations_per_bss`, `bss_spacing_m`, `station_radius_m`, `isolate_bss_channels`, `ssid_prefix`, `ap_sink_port`, `station_sink_base_port`, `generator_start_seconds` |
| `distribution` | `max_agents_per_station`, `low_contention_priority`, `slot_ms` |
| `wifi` | `band`, `channel_number`, `bandwidth_mhz`, `primary_20_index`, `rate_manager`, `active_probing` |
| `tcp` | `congestion_control`, `segment_size_bytes`, `send_buffer_bytes`, `receive_buffer_bytes` |
| `statistics` | `window_ms` |
| `logging` | `sample_scenario_level`, `ap_generator_level`, `sta_generator_level`, `traffic_sink_level`, `contention_distribution_level` |

Включенный в репозиторий
[`config/llm_config.toml`](config/llm_config.toml) имеет восемь секций и 35
заданных значений, потому что `run_folder` намеренно показан как
закомментированная необязательная настройка. В результате всегда есть все 36
полей, а пропущенный `general.run_folder` записывается как `null`. Значения
сохраняют имена TOML и скалярные типы JSON; строки перечислений используют
каноническое написание TOML. Настроенные строки путей сохраняются буквально.
Метаданные не содержат разрешенных путей, выходного пути, происхождения
настроек или статистики.

### Воспроизводимая живая проверка

После сборки `llm-scenario` инструмент живой проверки сопоставляет найденные
файлы с точной политикой из четырех трасс, проверяет каждый вход через
`find_window.py`, затем последовательно выполняет одну симуляцию для каждой
трассы. Используются уникальная папка
`/tmp/llm-trace-live.<trace>.<random>`, стандартный `output.json`, тайм-аут
политики и отсутствие переопределения имени результата.

| Трасса | Режим | Моделируемый диапазон | Тайм-аут |
|---|---|---:|---:|
| `1W_high_load_1s.json` | `auto` | полная трасса и настроенный хвост | 900 с |
| `1W_high_load_10s.json` | `auto` | полная трасса и настроенный хвост | 3600 с |
| `1W_high_load_1m.json` | `fixed` | 1.0 с | 1800 с |
| `1W_high_load_10m.json` | `fixed` | 1.0 с | 1800 с |

Сначала запустите детерминированные тесты чистых функций, ошибок и очистки,
затем реальную матрицу:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/live_test_traces.py --self-test
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/live_test_traces.py
```

Инструмент требует равенства найденных имен политике и проверяет точную
иерархию, плотный `overall` со ссылками на реестр, все флаги проверки,
конфигурацию 8/36, настроенный путь трассы, отсутствие удаленных корней и
старых отчетов. При ошибке печатаются трасса, команда, код возврата и последние
200 строк консоли. Каждая проверенная временная папка, созданная задачей,
удаляется в ветви `finally` после успеха, ошибки команды, тайм-аута или ошибки
разбора/формы; посторонние папки запусков никогда не удаляются. Для очистки
требуется Linux `renameat2` с `RENAME_NOREPLACE`. Случайная генерация имен
папки запуска и карантинной записи обеспечивает выбор имен с низкой
вероятностью коллизии. Папки запуска с режимом 0700, sticky-бит у `/tmp`,
сохраненные дескрипторы родительской и дочерней папок с `O_DIRECTORY` и
`O_NOFOLLOW`,
перемещения без замены и удаление относительно дескриптора без перехода по
ссылкам защищают пути других пользователей и отклоняют случайную подмену. Ни
одна из этих мер не дает гарантий безопасности от вредоносного параллельного
процесса с тем же эффективным UID ни на одном этапе жизненного цикла. Такой
процесс считается доверенным от создания и получения временной папки до
завершения очистки.
В частности, он может выполнить гонку до фиксации исходной идентичности на
этапе получения папки и после финальной проверки идентичности перед `rmdir` по
имени пути; случайность имен не защищает от процесса с тем же эффективным UID.

## Wi-Fi-бенчмарк насыщенного TCP

[`saturated-tcp-scenario`](examples/saturated-tcp-scenario.cc) является
независимым калибровочным бенчмарком 802.11ax. Он не загружает LLM-трассу, не
распределяет агентов и не использует генераторы трафика воспроизведения трасс.
Каждый запуск создает ровно три BSS и измеряет одну секунду неограниченного
TCP-трафика при заданных числе станций, RSSI полезной линии, политике видимости
между BSS, направлении трафика и пространственном режиме.

### Топология, распространение и пространственный режим

Каждый BSS имеет собственный проводной сервер, линию point-to-point 10 Гбит/с
с задержкой 0,1 мс, маршрутизирующую AP и настроенное число STA. Серверы и
проводные линии не разделяются. Все AP и STA используют 802.11ax, канал 42 в
диапазоне 5 ГГц, ширину 80 МГц, индекс основного 20-МГц канала 0, фиксированную
мощность 20 дБм, MinstrelHt, две антенны и не более двух пространственных
потоков на передачу и прием. Цвета BSS у AP равны 1, 2 и 3.

Расстояния вычисляются по тем же стандартным детерминированным моделям
распространения ns-3, которые используются во время запуска:

- `YansWifiChannel` как абстракция канала;
- `LogDistancePropagationLossModel` для мощности приема;
- `ConstantSpeedPropagationDelayModel` для задержки;
- без модели замираний и без переопределения MCS, скорости, RSSI, SIR или SINR.

Целевые значения полезной линии AP/STA проверяются в обоих направлениях до
начала трафика:

| `rssi_range` | Целевой RSSI |
|---|---:|
| `high` | -41.5 дБм |
| `medium` | -50.0 дБм |
| `low` | -60.0 дБм |

Каждая цель должна находиться в пределах +/-0,5 дБ. AP размещаются в вершинах
равностороннего треугольника, стандартные линии AP/AP которого имеют цель
-50,0 дБм. STA равномерно размещаются на окружности вычисленного радиуса
вокруг своей AP; каждый BSS имеет детерминированное угловое смещение.

Видимость между BSS намеренно ограничена:

| Связь отправителя и получателя | `isolated` | `ap_only_cochannel` |
|---|---|---|
| Один BSS, любая пара AP/STA | Стандартное распространение | Стандартное распространение |
| Разные BSS, AP с AP | Невозможно: разные каналы | Стандартное распространение |
| Разные BSS, любая линия с STA | Невозможно: разные каналы | Блокируется |

Таким образом, в `ap_only_cochannel` границы BSS пересекают только сигналы
AP-to-AP. Фильтр меняет только видимость: каждая разрешенная линия без
изменений передается стандартной модели LogDistance. Это программное
допущение бенчмарка, а не утверждение о физическом распространении 802.11.

Сейчас бенчмарк поддерживает только `mimo_mode = "su"`. В режиме SU одна AP
может использовать до двух пространственных потоков с одной STA 2x2. В
используемой версии ns-3 планировщик для нескольких пользователей не
поддерживает планируемый DL MU-MIMO, а доступный планируемый многопользовательский
путь UL является OFDMA, а не MU-MIMO. Поэтому конфигурация и скрипт отклоняют
`mu` и никогда не обозначают результат SU или OFDMA как MU-MIMO.

### Насыщенный трафик, готовность и область только STA

Для каждого активного направления каждая STA получает независимое
TCP-соединение:

- `ul`: отправитель STA и приемник на проводном сервере своего BSS;
- `dl`: отправитель на проводном сервере и приемник этой STA;
- `ul_dl`: оба соединения одновременно на разных портах.

Специализированный отправитель бенчмарка подключается без преждевременной
передачи, затем заполняет буфер сокета без ограничения числа байтов или
скорости приложения. TCP использует `ns3::TcpHighSpeed`, сегменты по 1460 байт
и буферы отправки и приема по 32 МиБ, то есть ровно по 33554432 байт. Начало
измеряемой нагрузки определяется событиями, а не фиксированным прогревом
трафика:

1. Установить приемники в момент времени ноль, дать ассоциациям одну секунду,
   затем запускать установку TCP-соединений в стабильном порядке потоков с
   интервалом 10 мс.
2. Дождаться ассоциации каждой STA и подключения каждого активного отправителя.
3. Выбрать первую целую секундную границу строго после полной готовности.
4. Запустить все отправители и сборщики метрик в эту общую эпоху.
5. Измерять ровно одну секунду, затем остановить, завершить сбор, проверить и
   закончить симуляцию.

Исчерпавшая попытки группа соединения сокета трассируется и через одну секунду
повторяется новым сокетом с теми же конечными точками и TOS. Глобальный
защитный тайм-аут 400 секунд превращает отсутствие готовности в ошибку; ни
повтор, ни тайм-аут не запускают нагрузку или статистику раньше времени. При
максимальных 180 потоках детерминированная установка начинается от 1,00 до
2,79 секунды, но измеряемая эпоха по-прежнему выбирается только после полной
готовности.

PHY-метрики бенчмарка включают только подходящие PPDU, переданные STA. Передачи
AP никогда не входят в значения STA или BSS, в том числе в режиме `dl`.
Подходят одноадресные данные, кадры данных TCP ACK, MAC ACK и BlockAck,
связанные с трафиком управляющие кадры, агрегация и каждая повторная попытка.
Beacon, ассоциация/пробы, широковещательный и посторонний трафик исключаются.

### Метрики STA, null в окнах и агрегация BSS

Для каждой STA сырые аккумуляторы хранят полное эфирное время подходящих PPDU,
произведение номинальной скорости `WifiTxVector` на это время, число битов
подходящих PSDU и объединение интервалов ожидания EDCA. Полное эфирное время
включает преамбулу, заголовки PHY и передачу полезной нагрузки. Биты PSDU
включают байты MAC/IP/TCP и повторные копии при ретрансляции.

Четыре производных поля STA:

```text
average_theoretical_phy_rate_mbps =
  sum(nominal_rate_bps * ppdu_airtime_seconds)
  / sum(ppdu_airtime_seconds)
  / 1,000,000

average_practical_phy_rate_mbps =
  sum(qualifying_psdu_bits)
  / sum(ppdu_airtime_seconds)
  / 1,000,000

channel_efficiency =
  average_practical_phy_rate_mbps
  / average_theoretical_phy_rate_mbps

contention_fraction =
  union_edca_waiting_time / statistics_window_duration
```

Ожидание EDCA включает AIFS, отсчет backoff и замороженный backoff, пока есть
хотя бы одна ожидающая очередь. Одновременные категории доступа объединяются,
поэтому `contention_fraction` остается в `[0, 1]`. Скорости принятых байтов
прикладного уровня не входят в эти уравнения или экспортируемые столбцы
бенчмарка.

Запись AP является агрегатом BSS, вычисленным по STA. Для настроенных STA
одного BSS:

```text
avg_all_sta_theoretical_phy_rate_mbps =
  mean(defined STA average_theoretical_phy_rate_mbps values)

avg_all_sta_practical_phy_rate_mbps =
  mean(defined STA average_practical_phy_rate_mbps values)

bss_channel_efficiency =
  avg_all_sta_practical_phy_rate_mbps
  / avg_all_sta_theoretical_phy_rate_mbps

bss_channel_contention_fraction =
  mean(all configured STA contention_fraction values)
```

PPDU, созданные AP, и конкуренция AP не используются. Если в коротком окне у
STA есть конкуренция, но нет подходящего PPDU, теоретическая и практическая
скорости и эффективность равны null; STA исключается из средних скоростей, но
ее конкуренция учитывается. Сущность без PPDU и конкуренции отсутствует в
разреженном окне, полностью неактивное окно также отсутствует. Плотная секция
`overall` содержит все настроенные STA и требует числовую конкуренцию каждой
STA, включая числовое `0.0`. Если за полную измеряемую секунду STA не передала
ни одного подходящего PPDU, ее общие теоретическая скорость, практическая
скорость и эффективность равны JSON `null`; такая STA исключается из средних
скоростей BSS, но ее конкуренция учитывается. Если ни одна STA BSS не имеет
определенной скорости, теоретическая скорость, практическая скорость и
эффективность BSS также равны `null`. Общие значения строятся заново из сырых
аккумуляторов, а не из средних округленных окон.

### Контракт JSON

Каждый прямой запуск эксклюзивно записывает один JSON-файл с отступом в два
пробела и существующим порядком семи корневых полей. Начальная конфигурация и
скрипт матрицы называют его `output.json`:

```text
schema_version
measurement_semantics
statistics_window_ms
windows
overall
validation
experiment_metadata
```

Каждый объект `phy_stats` AP/STA в окне и `overall` начинается с полей:

```text
average_theoretical_phy_rate_mbps
average_practical_phy_rate_mbps
channel_efficiency
contention_fraction
```

Для STA эти поля описывают передачи данной станции, для AP они содержат
вычисленные по STA формулы BSS выше. Остальные общие категории остаются в
стандартной форме с нулями/null. При стандартном окне 10 мс и насыщенном
трафике корректная прямая проверка содержит 100 окон, три AP и
`3 * sta_count_per_bss` STA. Конфигурация находится в
`experiment_metadata.configuration`, плотный список идентичностей -- в
`experiment_metadata.entity_inventory`, а все восемь общих флагов
`validation` должны быть равны `true`.

### Конфигурация и команды

Полная начальная конфигурация находится в
[`config/saturated_tcp_config.toml`](config/saturated_tcp_config.toml).
Исполняемый файл одного запуска применяет скомпилированные значения, затем
TOML, затем CLI-переопределения с префиксом секции. Секции называются
`general`, `script`, `simulation`, `benchmark`, `wifi`, `tcp`, `statistics` и
`logging`. Координаты матрицы:

| Поле | Фиксированные значения скрипта |
|---|---|
| `sta_count_per_bss` | 5, 10, 15, 20, 25, 30 |
| `rssi_range` | `high`, `medium`, `low` |
| `interference_mode` | `isolated`, `ap_only_cochannel` |
| `traffic_mode` | `ul`, `dl`, `ul_dl` |
| `mimo_mode` | Только `su` |
| `script.repetitions` | Положительное число попыток; стандартно 1 |

C++-программа записывает `script.repetitions` как метаданные, но выполняет
ровно один запуск; цикл по попыткам есть только в Python-скрипте. Если
`general.run_folder` пропущен, прямой запуск эксклюзивно создает
`run/saturated_tcp_<timestamp>`; явно указанная папка используется как точное
место результата. Имя JSON никогда не перезаписывается. Прямой запуск принимает
от 1 до 30 STA на BSS, а скрипт использует только шесть перечисленных значений.
`statistics.window_ms` должен быть положительным и делить 1000 без остатка.

Команды выполняются из внешнего корня ns-3:

```bash
./ns3 run "saturated-tcp-scenario --config contrib/llm/config/saturated_tcp_config.toml"
python3 contrib/llm/exp_scripts/saturated_tcp_experiment.py
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s contrib/llm/exp_scripts/tests -t contrib/llm/exp_scripts -p 'test_*.py' -v
```

Первая команда запускает стандартный вариант с 5 STA, высоким RSSI,
изоляцией, UL и SU. Вторая выполняет полную последовательную матрицу. Скрипт
фиксирует `rng_seed = 12345` и задает `rng_run` равным номеру повторной
попытки. Повторы сохраняются как отдельные результаты и никогда не
усредняются.

При стандартном одном повторе точная матрица только с SU равна:

```text
6 чисел STA * 3 диапазона RSSI * 2 режима интерференции * 3 режима трафика * 1 режим SU
  = 108 запусков ns-3
108 запусков * 3 строки BSS = 324 строки CSV
```

### Результаты скрипта, сохранение и фиксированный CSV для Excel

Скрипт выполняет по одному процессу ns-3 в стабильном порядке матрицы и
создает новое дерево во внешнем каталоге запусков, не перезаписывая пути:

```text
run/scripted_exp_<timestamp>/
|-- results.csv
|-- experiment_001/
|   `-- attempt_1/
|       |-- output.json
|       |-- stdout.log
|       `-- stderr.log
|-- experiment_002/
|   `-- attempt_1/
|       |-- output.json
|       |-- stdout.log
|       `-- stderr.log
`-- ...
```

Каждый JSON проверяется до добавления ровно трех строк BSS. Ошибка процесса,
тайм-аут, ошибка пути, метаданных, схемы, реестра, формулы, диапазона или флага
проверки немедленно останавливает матрицу. Неудачная попытка не добавляет строки
CSV. `results.csv`, JSON завершенных попыток и все логи попыток сохраняются для
аудита; скрипт не удаляет успешные или неудачные свидетельства.

Существует ровно один CSV с ровно 133 фиксированными столбцами: девять
столбцов идентичности, четыре столбца BSS и четыре столбца для каждого индекса
STA от 0 до 29. Их порядок:

```text
experiment_id
repetition_attempt
sta_count_per_bss
rssi_range
target_rssi_dbm
interference_mode
traffic_mode
mimo_mode
bss_id

avg_all_sta_theoretical_phy_rate_mbps
avg_all_sta_practical_phy_rate_mbps
bss_channel_efficiency
bss_channel_contention_fraction

для каждого i = 0, ..., 29:
  sta_i_avg_theoretical_phy_rate_mbps
  sta_i_avg_practical_phy_rate_mbps
  sta_i_efficiency
  sta_i_contention_fraction
```

В этом шаблоне десятичное значение `i` буквально подставляется по возрастанию:
первый блок начинается с `sta_0_avg_theoretical_phy_rate_mbps`, последний -- с
`sta_29_avg_theoretical_phy_rate_mbps`; буквального столбца `sta_i` нет.

Одна строка соответствует одному BSS одной повторной попытки и однозначно
определяется `experiment_id + repetition_attempt + bss_id`. Столбцы STA с
индексом, отсутствующим в конфигурации, полностью пусты. Для существующей STA
без подходящего общего PPDU пусты только ячейки теоретической скорости,
практической скорости и эффективности; ячейка конкуренции остается числовой,
включая `0.0`. Три ячейки скорости/эффективности BSS аналогично пусты только
тогда, когда в BSS нет определенной скорости STA, а конкуренция BSS остается
числовой. Дополнительных диагностических столбцов нет; подробная диагностика
остается в каждом сохраненном JSON.

Для прямого открытия в Microsoft Excel контракт CSV задает разделитель
точка с запятой, UTF-8 с BOM, окончания строк CRLF, десятичную точку и
стандартное экранирование двойными кавычками.

## Проверка IEEE 802.11: воспроизведение трасс в `llm-scenario`

Эта проверка относится только к сценарию воспроизведения трасс
`llm-scenario`. У насыщенного TCP-бенчмарка есть собственные топология и
ограничения, описанные выше: он фиксирует канал 42 и 80 МГц, задает AP цвета
BSS 1/2/3 и предлагает `isolated` либо явную политику видимости
`ap_only_cochannel`. Приведенные ниже утверждения о канале 0,
`isolate_bss_channels` и отсутствии явной настройки цветов не относятся к
`saturated-tcp-scenario`.

### Что корректно настраивает и моделирует `llm-scenario`

| Область | Результат проверки |
|---|---|
| Выбор стандарта | `WIFI_STANDARD_80211ax` включает поведение HE PHY/MAC в ns-3 |
| Инфраструктурная топология | MAC точки доступа и не-AP STA с ассоциацией по SSID |
| Ширины канала | Схема допускает 20/40/80/160 МГц; итоговый кортеж стандарт/диапазон/канал проверяет ns-3 |
| Кортеж канала | `{number, width, band, primary20}` соответствует семантике ns-3 `ChannelSettings` |
| Обмен кадрами | MAC/PHY ns-3 обрабатывает data frames, ACK, очереди, агрегацию, повторы и выбор скорости |
| Время PHY | Длительность PPDU вычисляется активной PHY-сущностью и TXVECTOR |
| Состояние среды | TX, RX и CCA_BUSY приходят из `WifiPhyStateHelper` |
| Ассоциация | `StaWifiMac` выполняет ассоциацию; активный поиск настраивается |

Номер канала 0 не означает канал IEEE 0. В ns-3 это значение
«не задано». После определения стандарта, диапазона и ширины ns-3 выбирает
первый допустимый канал. Например, реальная 20-МГц сеть 5 ГГц обычно явно
задает регуляторный канал вроде 36, а `llm-scenario` намеренно использует
стандартное значение ns-3.

### Важные допущения и отклонения модели `llm-scenario`

1. **Это не тест соответствия.** ns-3 реализует значительную часть 802.11, но
   остается абстрактной дискретно-событийной моделью. Успешный запуск
   `llm-scenario` не доказывает соответствие оборудования или прошивки.
2. **Стандартная изоляция BSS в `llm-scenario`.** Его стандартные отдельные
   объекты `YansWifiChannel` дают более сильную изоляцию, чем простое
   назначение разных каналов IEEE. Для одного общего моделируемого канала
   задайте `topology.isolate_bss_channels = false`; абстракция Yans при этом
   сохраняется.
3. **Нет регуляторного домена.** Не настроены country code, DFS, ограничения
   мощности и доступность каналов в `llm-scenario`.
4. **Нет явного OFDMA-планировщика.** AP не агрегирует многопользовательский
   планировщик ns-3, поэтому HE multi-user/OFDMA в `llm-scenario` не включен.
5. **Функции, не настраиваемые явно в `llm-scenario`.** Он не настраивает
   MU-MIMO, beamforming, BSS coloring, OBSS-PD spatial reuse, TWT и
   безопасность. Выбор 802.11ax сам по себе не запускает все функции
   дополнения.
6. **Абстракция Yans PHY.** Стандартный Yans PHY в `llm-scenario` работает на
   уровне пакетов, не является частотно-селективным и использует аналитические
   модели приема и ошибок. Он не моделирует стены, подробную геометрию кампуса
   и интерференцию от технологий, отличных от Wi-Fi.
7. **Выбор скорости зависит от модели.** Текущий исходный код MinstrelHt
   поддерживает HE-группы, но документация ns-3 перечисляет известные проблемы
   MinstrelHt и 802.11ax. Результаты `llm-scenario` зависят от версии ns-3.
8. **Задержка обработки здесь не является механизмом 802.11.** Длительность из
   трассы задает момент выпуска DL-данных в `llm-scenario`; задержка обработки
   Wi-Fi не выводится из стандарта.

Таким образом, конфигурация `llm-scenario` подходит для контролируемых
**экспериментов воспроизведения трасс в режиме 802.11ax с изолированными BSS
или BSS на общем канале**, но ее нельзя называть полной реализацией
соответствия IEEE 802.11ax.

Официальные источники:

- [Архитектура и ограничения Wi-Fi в ns-3](https://www.nsnam.org/docs/models/html/wifi-design.html)
- [Руководство пользователя Wi-Fi ns-3 и настройка каналов](https://www.nsnam.org/docs/models/html/wifi-user.html)
- [Рабочая группа IEEE 802.11](https://www.ieee802.org/11/)

## Сборка и запуск

Команды выполняются из корня ns-3, а не из `contrib/llm`.

### Зависимости

Для сборки ns-3 нужны C++ toolchain, CMake, Ninja и Python. Для потоковой
обработки больших архивов дополнительно нужны `unrar` и `python3-ijson`. Для
загрузки трасс из репозитория нужен Git LFS.

Пример установки только через apt:

```bash
sudo apt install build-essential cmake ninja-build ccache python3 \
  python3-ijson unrar git-lfs
git lfs install
git lfs pull
```

### Конфигурация и сборка

```bash
./ns3 configure \
  --enable-examples \
  --enable-tests \
  --enable-logs \
  --enable-warnings \
  --enable-werror

./ns3 build llm-test llm-scenario saturated-tcp-scenario
```

### Запуск небольшого примера

```bash
./ns3 run "llm-scenario --config contrib/llm/config/llm_config.toml"
```

Каждый настоящий запуск требует ровно один `--config PATH`. `--config` и все
переопределения не зависят от позиции и могут встречаться только по одному
разу. Полную автоматически сформированную справку можно вывести без файла
конфигурации:

```bash
./ns3 run "llm-scenario --help"
```

Порядок объединения значений:

```text
compiled defaults < TOML values < CLI overrides
```

Имена переопределений образуются из секции и TOML-ключа в kebab-case.
Логические переопределения требуют точных значений `true` или `false` в
нижнем регистре. Неизвестные поля и флаги, дубликаты флагов, позиционные
аргументы, неверные скалярные типы и недопустимые сочетания полей прерывают
запуск с ошибкой и справкой.

### Полный справочник TOML и CLI

Восемь секций TOML содержат 36 полей. Поставляемая конфигурация задает 35 из
них; необязательное `general.run_folder` намеренно закомментировано, чтобы
показать автоматическое создание папки запуска.

#### `[general]`

| Поле TOML | Переопределение CLI | Значение по умолчанию / смысл |
|---|---|---|
| `trace_file` | `--general-trace-file` | Обязательная входная JSON-трасса |
| `run_folder` | `--general-run-folder` | Не задано; точная выходная папка при наличии |

| `fixed_duration_seconds` | `--simulation-fixed-duration-seconds` | `0.0`; в режиме fixed должно быть положительным |
| `auto_tail_seconds` | `--simulation-auto-tail-seconds` | `2.0`; неотрицательный запас после конца трассы |
| `rng_seed` | `--simulation-rng-seed` | `12345`; допустимый диапазон seed ns-3 от 1 до 4294944442 |

|---|---|---|
| `sample_scenario_level` | `--logging-sample-scenario-level` | `info` |
| `ap_generator_level` | `--logging-ap-generator-level` | `warn` |

логирования и поэтому сохраняет состояние, уже включенное через `NS_LOG`.

### Правила путей и результатов

Текущая рабочая папка процесса фиксируется один раз при запуске.
Относительные пути конфигурации, `general.trace_file` и
`general.run_folder` разрешаются относительно этой одной папки, а не папки с
TOML-файлом.

- Явный `general.run_folder` является точной выходной папкой. Недостающие
  родительские папки создаются, а уже существующая папка разрешена.
- Без `general.run_folder` программа создает
  `./run/YY-MM-DD_hh-mm-ss` по локальному времени запуска. Родительская
  `./run` может быть создана, но существующая папка с той же временной меткой
  считается коллизией, и запуск прекращается.
- `general.output_name` должен быть простым именем файла `.json`, а не путем.
  Итоговый путь равен `<run_folder>/<output_name>`; существующий файл никогда
  не перезаписывается.

Проверка, разрешение путей и подготовка папки завершаются до создания объектов
топологии ns-3. При запуске печатаются разрешенные пути конфигурации, трассы,
папки и результата, а также основные настройки длительности, топологии,
распределения, Wi-Fi, TCP, RNG и статистики. Итоговые сводки измерений всего
эксперимента записываются только в напечатанный выходной файл. Обычные
сообщения о запуске, ходе, ошибках и завершении, а также по-событийное и
отладочное логирование остаются доступными. Его метаданные сохраняют
настроенные строки путей и не копируют эти разрешенные пути в JSON.

Пример с фиксированной длительностью:

```bash
./ns3 run \
  "llm-scenario --config contrib/llm/config/llm_config.toml \
  --general-trace-file contrib/llm/traces/1W_high_load_10m.json \
  --general-run-folder build/high-load \
  --general-output-name high-load.json \
  --wifi-bandwidth-mhz 80 \
  --simulation-duration-mode fixed \
  --simulation-fixed-duration-seconds 600"
```

Десятиминутная трасса высокой нагрузки велика и может потребовать
значительного времени симуляции и памяти.

## Инструменты для больших трасс

JSON внутри отслеживаемых RAR-файлов занимают несколько гигабайт. Не следует
распаковывать и загружать их через Python `json.load()` или передавать RAR
напрямую в `llm-scenario`. Используйте потоковый CLI с ограниченной памятью.

Справку потокового CLI можно вывести из корня ns-3 командой:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/find_window.py --help
```

### Проверка JSON или RAR

```bash
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/find_window.py \
  validate contrib/llm/traces/1W_端侧优先_tw6m_s42_w10000_st1000_mp_window_detailed_trace_w349000-359000.rar
```

### Запись первой подходящей минуты

```bash
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/find_window.py \
  slice-first INPUT.rar build/first-minute.json --window-seconds 60
```

### Поиск десяти минут с наибольшим числом байтов

```bash
PYTHONDONTWRITEBYTECODE=1 python3 contrib/llm/scripts/find_window.py \
  find-window INPUT.rar build/high-load-10m.json --window-minutes 10
```

Нагрузка окна равна сумме `uplinkBytes + downlinkBytes` сетевых операций,
целиком находящихся внутри окна. Граничные события накапливаются во временной
базе SQLite, поэтому потребление памяти не растет с числом операций. При
равной нагрузке выбирается самое раннее окно.

При записи скрипт:

- оставляет только задачи хотя бы с одной сетевой операцией внутри окна;
- сохраняет полностью попавшие в окно локальные операции таких задач;
- удаляет пустые трассы и задачи;
- переводит смещения операций и время прихода задач к началу нового окна;
- удаляет из зависимостей ID исключенных операций;
- сохраняет метаданные корня, трассы, задачи и операции;
- атомарно заменяет выходной файл;
- удаляет временные SQLite и выходные файлы при успехе или ошибке.

## Тестирование и отладка

### Тесты модуля

```bash
./test.py -s llm
```

Покрываются разбор трассы, обе политики распределения, порядок расписания,
`AppTxTag`, время барьера и фатальные инварианты, типизированная конфигурация
TOML/CLI, безопасные пути запуска, варианты топологии, атрибуция статистики и
JSON.

### Зарегистрированные smoke-тесты примеров

Пример требует `--config`, поэтому его зарегистрированный параметризованный
вариант выбирается маской:

```bash
./test.py -e 'llm-scenario*'
./test.py -e 'saturated-tcp-scenario*'
```

Команда `./test.py -e llm-scenario` без `*` запускает программу без
зарегистрированных аргументов; она сообщает об отсутствующей конфигурации и
выводит справку. Запись насыщенного бенчмарка выполняет детерминированную
прямую проверку с одной STA, проверяет JSON и удаляет только этот smoke-файл.

### Тесты скрипта насыщенного бенчмарка

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s contrib/llm/exp_scripts/tests -t contrib/llm/exp_scripts -p 'test_*.py' -v
```

Эти тесты проверяют точный порядок 108 конфигураций, связь повторов с RNG,
строгую проверку JSON, восстановление формул, fail-fast-владение процессами,
сохраненные пути и фиксированный контракт CSV для Excel без запуска дорогой
реальной матрицы.

### Тесты потоковых скриптов

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s contrib/llm/scripts/tests -t contrib/llm/scripts -p 'test_*.py' -v
```

Тестируются потоковая проверка, числовые границы, сохранение метаданных,
границы окон, очистка SQLite, атомарная запись, CLI и обработка stderr
процесса RAR.

### Логирование

Секция `[logging]` независимо настраивает компоненты:

- `SampleScenario` на уровне INFO;
- `ContentionAwareAgentDistribution` на уровне INFO;
- `APGenerator`, `StaLlmGenerator` и `TrafficSink` на уровне WARN.

Для запуска отладчика:

```bash
./ns3 run "llm-scenario --config contrib/llm/config/llm_config.toml" \
  --command-template="gdb --args %s"
```

При запуске в отладчике передайте обычные аргументы программы через команду
`./ns3 run`.

## Глоссарий

| Термин | Значение в проекте |
|---|---|
| Агент | Идентичность LLM-нагрузки прикладного уровня, не узел ns-3 |
| Операция | Шаг трассы со временем и возможными двунаправленными байтами |
| Задача | Контейнер связанных операций одного агента |
| Эпоха трассы | Общее время симуляции, соответствующее нулевому смещению |
| AP | Точка доступа IEEE 802.11, одна на BSS |
| STA | Физическая не-AP Wi-Fi-станция, может содержать много агентов |
| BSS | Одна AP, ее STA, SSID и объект канала |
| UL / uplink | Трафик STA -> AP в момент `startOffsetMs` |
| DL / downlink | Трафик AP -> STA в момент `startOffsetMs + durationMs` |
| MAC | Уровень управления доступом к среде Wi-Fi |
| PHY | Абстракция физического уровня Wi-Fi |
| MPDU | Протокольный блок MAC, то есть MAC-кадр |
| PSDU | Сервисный блок PHY: один или несколько MPDU для PHY |
| PPDU | Протокольный блок PHY, передаваемый в канал |
| A-MPDU | Агрегированный набор MPDU в одной PHY-передаче |
| TXVECTOR | Параметры PHY-передачи, включая режим и скорость |
| CCA_BUSY | PHY сообщает, что основной канал занят |
| RTT | Измерение времени прохождения туда и обратно TCP |
| AppTxTag | Байтовый тег, связывающий прикладную отправку с PHY |
| Тегированные байты | Диапазон прикладной нагрузки с `AppTxTag` |
| Уникальные байты | Тегированные байты только первой наблюдаемой попытки |
| Airtime | Модельная длительность PPDU, распределенная по тегированным байтам |
| Разреженное окно | Бакет настроенной ширины, выводимый только при наличии трафика |

## Ограничения по исполняемым файлам

Следующие списки намеренно разделены по исполняемым файлам. Ограничения
воспроизведения трасс нельзя переносить на насыщенный бенчмарк, а допущения
бенчмарка нельзя переносить на `llm-scenario`.

### Воспроизведение трасс в `llm-scenario`

- C++-парсер `llm-scenario` загружает весь JSON в память. Используйте срезы, а
  не исходные многогигабайтные документы.
- `llm-scenario` воспроизводит только операции с положительными байтами в
  обоих направлениях.
- Метаданные LLM, токенов и модели не влияют на сетевое поведение
  `llm-scenario`.
- По умолчанию BSS в `llm-scenario` используют физически изолированные объекты
  канала. Его необязательный режим общего канала моделирует взаимодействие в
  общей среде, но не подходит для подробного изучения пространственного
  переиспользования OBSS.
- `llm-scenario` не моделирует подробную радиосреду здания или кампуса.
- `llm-scenario` явно не настраивает OFDMA, MU-MIMO, beamforming, TWT,
  BSS coloring, OBSS-PD, аутентификацию и шифрование.
- Измерения PHY-нагрузки включают повторы. Для дедуплицированной нагрузки
  из результата `llm-scenario` используйте
  `phy_stats.*.unique_tagged_payload_bytes`.
- Диагностика уровня устройства `размер пакета - 60` в `llm-scenario`
  приблизительна.
- Сопоставление TX/RX в `llm-scenario` использует кортеж и порядок наблюдения.
  Это диагностика, а не формальный монитор потока.
- Прикладная длительность из трассы и задержка Wi-Fi/TCP в `llm-scenario`
  являются разными величинами.
- Результаты `llm-scenario` могут меняться между версиями ns-3, потому что
  модели Wi-Fi и алгоритмы выбора скорости продолжают развиваться.

### Бенчмарк насыщенного TCP

- `saturated-tcp-scenario` является контролируемой калибровочной топологией, а
  не универсальным конфигуратором Wi-Fi: он фиксирует три BSS, канал 42,
  80 МГц, 20 дБм, MinstrelHt и радиоустройства 2x2.
- Поддерживается только SU. Значение `mu` отклоняется, потому что эта версия
  ns-3 не имеет планируемого DL MU-MIMO, а ее доступный планируемый
  многопользовательский путь UL является OFDMA, а не MU-MIMO.
- `ap_only_cochannel` является явным программным допущением видимости: границы
  BSS пересекают только сигналы AP/AP, а любая меж-BSS линия с участием STA
  блокируется. Это не утверждение о физическом распространении.
- Метрики бенчмарка и поля CSV вычисляются только по подходящим PPDU,
  переданным STA. Передачи AP и скорости байтов прикладного уровня не входят в
  эти формулы.
- Бенчмарк использует пакетный Yans PHY со стандартными детерминированными
  потерями LogDistance, без замираний и модели здания. Результаты MinstrelHt
  остаются зависимыми от версии ns-3.

Для точного поведения обращайтесь к реализации выбранного исполняемого файла
и официальной документации Wi-Fi ns-3 по ссылкам выше.
